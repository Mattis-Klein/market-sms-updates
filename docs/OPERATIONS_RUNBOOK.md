## Startup Sequence

1. Start backend API.
2. Confirm `/health` responds with `{ "ok": true }`.
3. Verify Twilio webhook points to `/api/market-updates/sms`.
4. Send test SMS: `MENU`.

## SQLite -> PostgreSQL Migration Sequence

1. Stop worker processing (or run migration during maintenance window).
2. Confirm source SQLite path exists and is healthy.
3. Run migration:

```bash
cd backend
../.venv/Scripts/python.exe scripts/migrate_sqlite_to_postgres.py --sqlite-path data/market_updates.sqlite --database-url "$DATABASE_URL"
```

4. Validate row counts in key tables (`market_assistant_sessions`, `market_scheduled_reminders`, allowlist tables).
5. Switch runtime config so both web and worker use `DATABASE_URL`.
6. Keep SQLite backup generated by migration script for rollback.

Safety notes:
- Migration refuses by default if destination PostgreSQL already has data.
- Use `--force-if-destination-nonempty` only during controlled, reviewed operations.

## Post-Deploy Smoke Tests

- `MENU` returns numbered guidance list.
- `3` returns symbol lookup instructions.
- `SYMBOL S&P` includes `^GSPC`.
- `TICKERS` returns supported symbols.
- Direct ticker like `$AAPL?` returns quote.
- `BEAST` and `@mrbeast` return subscriber count or fallback message.
- `@assist` returns: `How can I assist you today?`
- `@assist` then `What is the weather right now?` forces Responses API web search and returns either current sourced result or: `I couldn't access live information right now. Please try again shortly.`
- `menu` while in assistant mode is handled by AI (does not exit assistant mode).
- `@exit` exits assistant mode and returns close message.
- `@assist` then `Remind me in half an hour to call my brother` should return a scheduled confirmation with resolved time.
- Run web and worker as separate processes pointing to same `DATABASE_URL`; verify reminder is created by web then delivered by worker.

## Production Readiness Gate

Do not declare production-ready until this has been observed in the deployed environment:
- reminder creation event from web process,
- reminder claim/send event from separate worker process,
- both against the same persistent PostgreSQL database.

## Troubleshooting

### No SMS reply

Check in order:
1. Twilio webhook URL and HTTP status.
2. Backend process health and logs.
3. Allowlist status for sender number.
4. Whether sender is stuck in a reminder session (commands should still bypass now).
5. If issue is assistant mode only, verify AI/search API keys and timeout settings.

### BEAST failures

Expected behavior on failure:
- Friendly fallback message should return.

If not:
- Inspect upstream connectivity to livecounts endpoints.
- Verify no unhandled exceptions in logs.

### Symbol lookup misses

- Use `SYMBOL <query>` first.
- For S&P, use `SYMBOL S&P` or symbol `^GSPC`.

### Assistant mode unavailable or slow

Check:
1. `OPENAI_API_KEY_PRIMARY` is set and valid.
2. `ASSISTANT_SEARCH_API_KEY` is set (required for web search context).
3. Timeouts: `ASSISTANT_AI_TIMEOUT_SECONDS` and `ASSISTANT_SEARCH_TIMEOUT_SECONDS`.
4. Logs for: `openai_primary_request_succeeded`, `openai_primary_failed_attempting_fallback`, `both_openai_providers_failed`.

If primary key fails, system automatically retries with `OPENAI_API_KEY_FALLBACK` (if set) on eligible errors:
- Authentication failures (401): Invalid, expired, or disabled primary key.
- Rate-limit errors (429): Primary project rate limit reached.
- Temporary server errors (5xx): Transient OpenAI outage.
- Connection/timeout errors: Network issues.

Primary key failure does NOT use fallback for:
- Invalid parameters or model.
- Content policy violations.
- Malformed request data.

Failure message to user:
> The AI assistant is temporarily unavailable. Please try again shortly or reply MENU to return to the main menu.

### Reminder worker deployment notes

- Preferred production architecture: web service for inbound SMS + dedicated background worker for reminders + shared persistent database.
- If using only SQLite attached to a single persistent disk, run worker in the same always-on service instance or co-locate service/worker with shared storage.
- Start dedicated worker with: `python -m market_updates.reminder_worker`.
- Optional in-web worker toggle: `REMINDERS_RUN_IN_WEB=true` (single always-running instance only).
